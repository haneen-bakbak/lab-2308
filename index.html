Overview

Overview & Architecture

Introduction & Lab Objectives

Risk and compliance teams need to understand where assessments are incomplete and document the work required to address them. In this lab, you will use an AI risk agent to query live IBM OpenPages data, explain an assessment gap, create a risk record, and link an existing control to that risk through plain-language requests.

IBM Bob handles setup using the supplied lab project. IBM watsonx Orchestrate runs the agent, and the Model Context Protocol (MCP) connects it to the OpenPages tools. You will inspect the recorded execution to understand how the agent obtained its evidence and carried out your requests.

The Scenario

You are a risk analyst at a financial institution. Controls in your assigned lab environment are marked Awaiting Assessment. Your task is to identify the affected risk categories, explain the findings, and document a gap for follow-up.

The guided prompts follow a connected workflow: find the gap, explain it, log a risk, and link a control. The category and record counts depend on the data in your environment. Use those results to guide the risk you document.

Interpreting the results

An unassessed control indicates an assessment gap. It does not, by itself, establish that a control has failed or that the organisation is non-compliant.

What You Will Learn

  • Use Bob to configure the supplied agent and integration assets.
  • Query live risk and control data using natural language.
  • Inspect how schema retrieval helps the agent use valid field names and permitted values.
  • Create a risk record and associate an existing control through explicit requests.
  • Check the resulting records in OpenPages and inspect the corresponding tool activity in Orchestrate.

Lab scope: You direct the workflow through prompts. The agent selects and executes the corresponding tools. This exercise demonstrates agent-assisted risk work rather than a complete control assessment or compliance determination.

Architecture & Request Flow

The solution separates setup from runtime. Bob prepares the agent on your workstation. Once setup is complete, you chat with the risk agent in watsonx Orchestrate (in your browser), and the agent accesses OpenPages through the MCP server.

Solution Architecture

Setup: Bob Configures the Agent

Open the supplied project in Bob and select Lab 2308 mode. Give Bob the MCP Server URL, watsonx Orchestrate Instance URL, and IBM Cloud API key you collect in the Prerequisites. Bob uses these values to configure the environment, register the MCP tools, and import lab2308_risk_agent.

Bob supports setup and troubleshooting. It is outside the runtime request path once the agent is available in Orchestrate.

Runtime: Orchestrate Calls OpenPages Through MCP

In Orchestrate Chat, select lab2308_risk_agent and submit a request. The agent selects the appropriate tools, and the MCP server translates those tool requests into OpenPages API calls. Results return through the same integration. Successful write operations change records or relationships in your assigned OpenPages environment.

The MCP server and OpenPages run in the same assigned TechZone environment. The /mcp endpoint serves tool requests. The /openpages endpoint opens the application where you can verify the records.

The Lab Conversation, Traced End to End

The sequence below follows the guided scenario across the participant, risk agent, MCP server, and OpenPages. It shows the system interactions behind the conversation, including the explicit requests to create a risk and link a control.

Why the Agent Reads the Schema First

OpenPages uses specific object types, field names, and permitted values. The agent uses openpages_get_resource to inspect relevant schemas, such as openpages://schema/SOXControl, before constructing operations that depend on those definitions. This reduces reliance on guessed field names and values. It does not guarantee that every request will succeed.

The scenario uses execute_openpages_query to retrieve records, openpages_upsert_object to create the risk, and openpages_associate_objects to link the control. Schema checks also apply to the relevant write operations.

Verify the Outcome and Inspect the Evidence

Open the new risk in OpenPages and check its fields and control relationship. Then return to Orchestrate and follow AgentOps → Observability → your agent → Conversations → Debug. Inspect the available schema responses, query payloads, write results, and execution timing to connect what the agent reported with what the tools returned.

2.0 Module 2 - Explore OpenPages GRC

Before chatting with the agent, spend a couple minutes exploring the source system it will be querying.

2.1 Log In to OpenPages

Open your OpenPages Application URL in your browser and log in with the credentials provided by your instructor.

2.2 Find the Risk Records

  1. Click the top-left Navigation Menu (hamburger icon).
  2. In the Search object type box at the top of the menu, type Risk and click the Risk entry. There is no tab called "Risk register" - the object type is simply called Risk.
  3. Notice the Resource ID format (e.g. I01-RSK-01-01 or numeric 21011).

What you should see: the Risks list

Take a minute to explore this list. It is the data your agent will query in Module 3.

  • Read the columns: Name (the Resource ID, for example I01-RSK-01-01), Description, Domain, Status and Residual Risk Rating.
  • Look at the Status column. Many risks show Awaiting Assessment. This is the kind of assessment gap your agent will find in Module 3.
  • Look at the Domain column (Financial Management, Operational, Compliance, Technology). The same risk name can appear more than once, under different business entities shown beneath the name (for example Global Financial Services > EMEA > Finance).

What you should see: a single risk record

Click a risk name, for example I01-RSK-01-01, to open it.

  • In the General section, find Name, Owner, Status, Description and Domain.
  • In the Risk Assessment section, find the Inherent and Residual Impact, Likelihood and Risk Rating.
  • Note the Status and Description of this risk. In Module 3 you will ask the agent about risks like this one, and later create a new one.
Labels vs. field names

These are the labels you see on screen. Behind them, OpenPages stores each one under an internal field name (for example, Status is OPSS-Rsk:Status). You never type these names: your agent reads them from the OpenPages schema at runtime, so it uses the exact field names instead of guessing.

3.2 Guided Test Prompts: The Compliance Scenario

You are a risk analyst at a financial institution. Every control in this environment is sitting at "Awaiting Assessment". Your job is to find the gap, log the risk, and link the control.

Prompt 1 - Find the Compliance Gap

Prompt 1

"Which of our risk categories have controls that are still awaiting assessment?"

Recommended: open "Show Reasoning" on this first answer

When the agent replies, click Show Reasoning next to the agent name, just above the answer. watsonx Orchestrate will share the agent's thought process: which tool it chose, the exact query it sent to OpenPages, and the raw data that came back. It is worth a look. It helps you understand what is happening behind the scenes, and it is the same evidence you will study in Module 4. Click Hide Reasoning to close it again.

Expected behavior: The agent calls openpages_get_resource to inspect the SOXControl schema, executes a query for controls with status Awaiting Assessment, groups them by OPSS-Shared-Basel:Risk Category, and highlights the most exposed category. The category depends on the data in your OpenPages environment - seeing Internal Fraud, External Fraud or another category is expected and fine.

Prompt 2 - Explain the Gap

Prompt 2

"Explain the gap briefly."

Expected behavior: The agent summarises which category has the most risks and notes how many controls are still awaiting assessment - a short plain-English explanation using the data already retrieved.

Prompt 3 - Create a New Risk Record in OpenPages

Prompt 3

"Log a new risk in OpenPages: Name it 'Inadequate Fraud Detection Controls', set the category to External Fraud, and note that controls are unassessed."

If your agent named a different category in Prompt 2, you can swap it (and a matching risk name) into the prompt above.

Expected behavior: The agent finds a parent process (e.g. Retail Banking), calls openpages_upsert_object with object_type: "soxrisk", and returns the newly assigned numeric Resource ID with a direct clickable link into OpenPages.

Prompt 4 - Associate the Control to the New Risk

Prompt 4

"Link control CTL-04-03-03-01 to our new Inadequate Fraud Detection Controls risk."

Expected behavior: The agent resolves the control ID, invokes openpages_associate_objects, and confirms the bidirectional relationship.

3.3 What the Agent Is Doing (Schema-First Pattern)

Every response follows this robust execution sequence:

User Prompt
    │
    ▼
1. openpages_get_resource("openpages://catalog/object_types")   ← Discover types
    │
    ▼
2. openpages_get_resource("openpages://schema/SOXRisk")          ← Introspect valid fields
    │
    ▼
3. execute_openpages_query(SELECT confirmed_fields FROM...)      ← Query with verified fields
    │
    ▼
4. Rewrite internal opapp URLs to external TechZone hostname     ← Format links
    │
    ▼
5. Synthesize and format Markdown response

4.2 Anatomy of an MCP Execution Trace

Span TypeComponentWhat It Reveals in the Trace
TOOL (Schema Discovery)openpages_get_resourceThe exact URI (openpages://schema/SOXControl) introspecting valid fields prior to query generation.
TOOL (Data Query)execute_openpages_queryThe SQL query payload, execution latency (ms), HTTP 200 response, and row count.

LLM SPAN (Reasoning)llama-3-3-70b-instructReAct reasoning steps, token counts, inference latency, and output formatting.
